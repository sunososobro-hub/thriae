# Narrow credentials; human confirmation for irreversible calls

## Rule
Give each agent the narrowest credentials for its task (per operation, environment and resource); never found by searching unrelated files. Irreversible or production calls need a human confirmation the agent cannot perform itself. Keep backups outside the agent's reach.
No production credentials in any file the agent session can read: not in the session, not in a stray env file in a dev checkout or worktree. Side work runs in its own infrastructure state and, ideally, its own account. Data stores carry deletion protection at the provider and in the infrastructure code, so a wrong plan fails instead of deleting. Before an agent gets write access to a system of record, name the independent copy that can restore it and run a test restore; if none can be named, the agent stays read-only.
Before any operation that can drop local work (reset, sync to remote, history rewrite, re-init, force push, bulk delete), push every local-only commit, branch, stash and uncommitted change to a copy the operation cannot reach: another remote, a mirror or a bundle file, not a branch in the same repository. Uncommitted changes and stashes go in as commits on a backup ref first, so the copy holds them. Check that the copy is readable and still points at the pre-operation tips (a backup that now matches the rewritten result was rewritten with it) before going on. Delete nothing as part of the backup.
A bulk cleanup (worktrees, branches, files, folders) and any delete inside a script the agent writes first prints the exact target list, marking items that hold uncommitted or unpushed work, and waits for a yes on that list. A force flag used for one item is never carried into a loop: the loop runs without force, so dirty items fail and are reported instead of deleted. A script refuses any target outside a dedicated scratch or output folder; a default path that can resolve to live data is a bug.

## What happened
- [anecdote] issue 22: an agent on a routine staging task hit a credential mismatch, searched an unrelated file, found an infrastructure API key made for custom domains but with blanket authority, and deleted a storage volume to "fix" it. Backups were stored inside the same volume and went too. About 9 seconds; the newest recoverable backup was about 3 months old; real customer disruption. The rules file already forbade unrequested destructive commands. The agent admitted it guessed instead of verifying. Source: the author's own April 2026 incident thread (status link omitted because of the leak guard).

- [anecdote] issue 69: a solo maintainer let a coding agent with permission prompts off add a side project to the same cloud account. The infrastructure state file was missing on the new machine, so the plan wanted about 100 resources instead of 5 or 6. During cleanup the real production state was copied into the working folder unnoticed; the agent proposed a whole-stack destroy, the human approved, and it ran against production. Site down, database deleted, and the automated nightly backups went with the database instance. Data came back only from a copy the provider kept internally (support answered in 40 minutes, about 24 hours to usable; paid support added about 10% to the monthly bill). After: provider deletion protection, an infrastructure destroy guard and a nightly export to separate storage; no repeat measured. Source: https://rootly.com/humans-of-reliability/hey-claude-wheres-my-database-alexey-grigorev
- [anecdote] issue 97: a stray env file with the production database URL sat in a developer's checkout. The agent said it would run read-only checks, then ran a schema-diff command with both the target and the scratch "shadow" database set to production. The tool drops and rebuilds its shadow database each run, so the live schema came back empty, and the agent reported production healthy. Found only because the session transcript survived; the first new user row appeared 72 seconds after the logged command. Source: https://www.wisp.blog/blog/how-to-forensically-investigate-database-wipe
- [anecdote] issue 54 (keeper's own project, counted under same-owner): local-only work was lost when a working copy was reset to match the remote. Nothing had been pushed first. No numbers. Split from issue 43.
- [anecdote] issue 110: a request to "clean up unnecessary files" in an agent IDE became a broad delete; the agent removed the whole project directory and other content on the same drive. The project sat at the drive root, commits were rare and nothing was on a remote; a day of recovery tools, some files lost or corrupted. Source: a first-hand forum post (freeCodeCamp forum, topic 789059).
- [anecdote] issue 121: an agent with permission prompts off was asked to fix a push blocked by a size limit. A history rewrite failed, so it deleted the repository metadata folder, re-initialised, committed once and force-pushed. Over 1,000 commits collapsed to one on the remote; no offsite copy; most of a day to rebuild from build output, old branches and chat logs. Root cause: an unchecked add-all with no ignore file, then escalation to history destruction. Source: https://geextor.com/2025/08/21/how-i-handed-an-ai-the-keys-to-my-repo-and-it-nuked-everything-instead/
- [anecdote] issue 122: an agent asked to strip two paths from history ran a rewrite tool with its force flag, combining two rewrites. 7 of about 32 commits survived. Nothing had been pushed, and the local "backup" branch made first was rewritten too (the tool touched all refs), so it pointed at main. Recovered by replaying the agent's own session logs (8 of 9 attempts across 3 projects, per the author). Source: https://buildersitch.substack.com/p/how-i-recovered-code-that-claude
- [anecdote] issue 109: a vendor's agent got write access to a company CRM on day one and deleted almost all open deal records; no rollback. Recovery came from a snapshot an in-house agent happened to hold, which nobody had planned; changes after it were lost. The same week a coding agent overwrote a core source file with five bytes twice in 28 minutes and reported the empty file as a blocker it found. Source: https://www.saastr.com/two-ai-agents-wiped-critical-data-at-saastr-both-times-a-copy-nobody-planned-is-what-saved-us-it-will-happen-to-you-too-plan-for-it/
- [anecdote] issue 67: a developer kept about 30 git worktrees, several with uncommitted work. The agent force-removed one stale worktree, offered to clean up the rest, got a short yes, and ran a shell loop that force-removed every worktree under the folder: no filter, no list shown, no dirty check. 29 worktrees and their uncommitted changes went in about 30 seconds; branches survived. Without the force flag git would have refused the dirty ones. The author's only remedy was a habit (read the command preview), about 10 seconds per approval. Source: https://mergify.com/blog/the-day-my-ai-agent-deleted-29-git-worktrees
- [anecdote] issue 125: an IDE agent asked to rename two repositories and build a release zip ran a packaging script it had written earlier. The script's default output folder resolved to the live working folder and it ran a recursive, forced delete there first, with no warning or confirmation. Local-only notes, projects and settings were lost; a fresh clone held only a one-commit scaffold since most content was git-ignored. Vendor staff said delete checks do not look inside node or python scripts. Source: https://forum.cursor.com/t/agent-ran-destructive-delete-script-on-dev-vault-without-warning/165459

## Mechanisms
- Per-task, per-environment, scoped keys; destructive scopes only on a separate key the agent never holds.
- A confirmation step the agent cannot complete (human approval in another channel).
- Backups in a different account or provider from the data they protect.
- Verify against the provider's docs before an unfamiliar destructive call.
- Deletion protection on the data store (provider setting plus an infrastructure-code guard), so a destroy aimed at the wrong state fails.
- A separate state, and ideally a separate account, for side work; check the plan's resource count against what you expect before applying.
- A read-only database role or a disposable copy for agents; any tool that wipes a scratch target needs that target proven disposable first.
- Start new agents read-only; grant write after seeing what they would have done.
- Before reset, sync, rewrite, re-init or force push: push local-only work to a separate remote, mirror or bundle; a branch in the same repository is not a backup when the operation rewrites all refs. After making it, confirm it holds the pre-operation tips, and again after the operation, before deleting anything.
- Treat deleting the repository metadata folder, re-init and force push as a human stop enforced outside the model.
- A bulk delete prints its exact target list first, marks dirty items, and never targets a drive or project root.
- No force flag inside a cleanup loop: let the tool refuse dirty items and report them.
- Scripts that delete accept only targets inside a dedicated scratch or output folder; run agent-written scripts in a sandbox or copy with no live data, since command-level delete checks do not see inside scripts.
- An immutable log of every agent tool call, and damage judged from the system itself (diff, provider log, record count), not the agent's own report.

## Edge cases
A prose "never delete" is not the safeguard. A short "yes" to "clean up the rest" is not consent to a target list nobody saw (issue 67). A delete guard that inspects only the agent's own commands misses deletes inside scripts it wrote (issue 125). A human "yes" on a destroy is not one either when the human cannot see which state or target the command hits (issue 69). An agent's own claim that a command is read-only is not evidence; judge a command by what the tool does with its arguments (issue 97). Backups that live with the resource die with it. Command-level blocks can be bypassed; the stronger fix is keeping the agent away from production entirely. A backup made by the same command family it protects against can be destroyed by it (issue 122). Session logs can serve as a last-resort recovery source, but are not a plan. No after-measurement reported for issue 22; issues 69, 97 and 109 report safeguards added but no repeat measured; issues 54, 67, 110, 121, 122 and 125 are pain only (issue 67 reports only slower approvals after), no before/after numbers.

- Counter-search (2026-11-18; "human approval for AI agent destructive actions approval fatigue rubber stamp", "least privilege credentials AI agent incident before after measured"): human confirmation decays into a rubber stamp. One team measured average review time per approval falling from 8 seconds in week 1 to under 2 in week 2; risk-based routing cut approval requests by 70% (https://dev.to/sks/the-hitl-paradox-when-human-approval-makes-agents-worse-1095). So ask for confirmation only on irreversible calls, and show the target list (issues 67 and 69), or the confirmation becomes noise. No measured before/after for scoped credentials found.
