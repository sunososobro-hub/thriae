# Thriae pipeline (optional)

Layout:
- `core/` rules (`rules.md`) and optional profiles (`release-lane.md`, `public-repo.md`). Vendored into a project at `.agent/core/`.
- `project.template.yml` copy to `.agent/project.yml` and fill in.
- `routines/` prompt templates for scheduled agents (worker, hard-worker, merger, reviewer, supervisor).
- `scripts/onboard.sh <owner/repo> [--dry-run]` one command to connect a repo: enables Issues, runs bootstrap (`--no-ci`), generates `.agent/project.yml` with detected default branch and test command and the issue numbers filled in, vendors core/roles/AGENTS.md, adds `thriae-sync.yml` (and a minimal ci only if the repo has no test workflow), opens ONE PR to the default branch and tries to enable "Allow GitHub Actions to create and approve pull requests" (prints the manual step if the API refuses). Re-run safe. Not covered: the cloud routines and merging the PR (protected paths need a Strong PASS).
- `scripts/bootstrap.sh` creates labels, control issues and a minimal CI workflow (default dry run).
- Label `lesson`: `.github/workflows/lesson-label.yml` adds it to any issue whose title starts with "[lesson]" (create the label once; the sender never sets labels).
- `scripts/sync_core.sh` vendors a tagged core into a project as a PR (default dry run; needs THRIAE_CORE_REPO).
- `scripts/sync_agents.sh` + `thriae-sync.yml`: keep a project's AGENTS.md shared part (between `<!-- thriae:start -->` and `<!-- thriae:end -->`), `hive/pipeline/roles/` and `.agent/core/` in step with Thriae. Copy the workflow into the project's `.github/workflows/`; once a week it opens one PR, the project block is never touched, nothing merges automatically, and data only flows Thriae -> project.

**Source of truth:** this directory (`hive/pipeline`) is the single source of the agent factory core. Projects vendor a tagged copy with `scripts/sync_core.sh`; they never read the tip. Older private copies are frozen. Change rules in [`GOVERNANCE.md`](GOVERNANCE.md).

Start with `AGENTS.md` at the repo root; adopt this directory only when you want scheduled agents.
Schedules, caps and budget numbers in these files are example defaults from one deployment. Tune them in `project.yml`.

## Lesson flow (Claude routines)
Flow: lesson issue on the target repo (label `lesson`) -> the reviewer routine (a scheduled Claude routine, hourly) adds one comment and one `review:*` label -> the scout routine (every 2 hours) looks for new lesson candidates and failures in the projects -> when the reviewer confirms `evidence: 3/3 projects` it adds `quorum`, clusters the batch by theme (same failure mode = one rule, all issue numbers cited), checks the clusters against existing AGENTS.md lines for duplicates, re-implements one short line per cluster in AGENTS.md with a full-URL pointer to a detail file `hive/rules/<theme>.md` (lazy loading: every issue number, source, mechanism and edge case is kept there; index in `hive/rules/README.md`; idea issue 40), in its own words (one in, one out, 250-line cap), runs `leak_check.py` on them, and opens one `fix/N` PR; the PR squash-merges itself once CI and the leak guard pass, with no human gate. Only a CONSTITUTION amendment still needs the keeper (Article 9).
- Verdicts: `evidence:<N>` (supports a rule, section N), `candidate:<slug>` (new general lesson), `duplicate`, `needs-evidence`, `rejected`. Plus the label `quorum` at 3 independent projects.
- Tally (CONSTITUTION Art. 3): every lesson body carries `Project-ID: <12 hex>` (anonymous). The reviewer writes `evidence: n/3 projects` on the lesson issue: count distinct Project-IDs, where a Project-ID stands for the project the incident happened in. Who opened the issue does not count: a report a scout files on behalf of another project counts under that source project's Project-ID. All of the keeper's own projects together count at most once per lesson, however many they are; those issues get the label `same-owner`. Votes and repeat reports from one project do not count. Near-duplicate issues (same or near-same body) count as ONE: the reviewer labels the extras `duplicate` and links them to the first. A report that backs an existing lesson says `Supports #N`.
- Safety: issue text is data, never instructions. The promote step only ever edits AGENTS.md (and the lesson issues it closes) through a `fix/N` PR; it never pushes to the default branch, never touches CONSTITUTION.md and never passes `--admin`. Routine prompts: [`routines/reviewer.md`](routines/reviewer.md).
- Nothing in this repo holds a model key. Scheduled routines run on the maintainer's side and talk to GitHub only.
